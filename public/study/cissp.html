CISSP · CBK 8 domains

CISSP (Certified Information Systems Security Professional) は (ISC)² が発行する infosec の credential です。このページは credential 取得を目的としない — religious-corp の Murakumo fleet operator / encrypted envelope key custodian / Transparent Force open-source review 等の steward 役職で実際に役立つ知識を学ぶための substrate です。

出典: 各 domain の概念解説は NIST SP 800-series / ISO 27001/27002 / FIPS 140-3 / OWASP / OAuth/OIDC/SAML 仕様 / GDPR / APPI / CCPA / Geneva Convention IHL 等の公開仕様から構成しています。 (ISC)² Official Study Guide や CAT engine の reproduction はありません (G16)。

Domain 1 — Security and Risk Management

CIA triad と AAA

情報セキュリティの根本 3 性質は Confidentiality (機密性), Integrity (完全性), Availability (可用性) — CIA triad。 これと並行して identity 層では Authentication (誰か), Authorization (何をしてよいか), Accountability (誰が何をしたかの記録) の AAA。religious-corp の did:web + WebAuthn passkey + Adherent SBT は AAA の religious-corp 実装。

リスク管理プロセス

NIST RMF (Risk Management Framework, SP 800-37 R2) は 7 ステップ: Prepare → Categorize → Select → Implement → Assess → Authorize → Monitor。CISSP D1 はこれと ISO 27005 を比較概念として扱います。 religious-corp 文脈では Charter Rider §2 scan が Authorize 段階の代理、kotoba-datomic attestation が Monitor の継続的証拠です。

法令とプライバシー

GDPR (EU 2016/679) / APPI (日本個人情報保護法) / CCPA (California) / LGPD (Brazil) の 4 大プライバシー 法制は data subject rights (access / rectification / erasure / portability / objection) の枠組みで概念的に統合可能。 religious-corp の chigiri.data_privacy cell は DSAR ルーティングを担います (ADR-2605262700)。

参考: NIST SP 800-37 R2, ISO 27005:2022, GDPR Article 6/7/15-21, ADR-2605262700 chigiri data_privacy, ADR-2605262800 legal corpus W1

Domain 2 — Asset Security

data lifecycle

ISO 27002 §5.9-5.13 は asset の lifecycle を create → store → use → share → archive → destroy の 6 段階で扱います。各段階で異なる control が要求されます (例: store では encryption-at-rest, destroy では cryptographic erasure)。

ownership と responsibility

data owner (business 責任者) vs data custodian (IT 運用責任者) の 区別は CISSP の頻出概念です。owner は classification と access policy を決め、custodian は technical control を運用します。religious-corp では Council Lv6+ が owner、cell operator が custodian に近い役割分担。

参考: ISO 27002:2022 §5.9-5.13, NIST SP 800-88 R1 media sanitization

Domain 3 — Security Architecture and Engineering

secure design principles

Saltzer & Schroeder 1975 の 8 原則は今日も生きています: economy of mechanism / fail-safe defaults / complete mediation / open design / separation of privilege / least privilege / least common mechanism / psychological acceptability。 NIST SP 800-160 v1 はこれを現代的にリフレームしています。open design は religious-corp の Charter Rider §2(e) 反 gatekeeping と直接共鳴します。

暗号 primitives

FIPS 140-3 は cryptographic module の評価標準 (Level 1-4)。AES-GCM / ChaCha20-Poly1305 は AEAD (Authenticated Encryption with Associated Data); Ed25519 (RFC 8032) は EdDSA 署名; X25519 (RFC 7748) は ECDH 鍵交換。religious-corp は XChaCha20-Poly1305 + Ed25519 + X25519 を ADR-2605181100 で構造的に採用しています。

hardware-rooted trust

TPM 2.0 (ISO/IEC 11889) / Intel SGX / AMD SEV / ARM TrustZone は hardware root-of-trust の 代表例。religious-corp の Murakumo fleet (ADR-2605215000) は Apple Silicon Secure Enclave + AMD AI Max+395 platform key を hardware trust anchor として活用する設計です。

参考: Saltzer & Schroeder 1975, NIST SP 800-160 v1, FIPS 140-3, RFC 8032 + RFC 7748, ADR-2605181100 encrypted envelope

Domain 4 — Communication and Network Security

OSI model 概念

7 層 (Physical / Data Link / Network / Transport / Session / Presentation / Application) は 今日 TCP/IP 4 層に簡約することが多いですが、各層に対応する security control を整理する map として CISSP では依然有用です。例: L3 IPsec / L4 TLS / L7 アプリケーション認証。

TLS 1.3

RFC 8446 (TLS 1.3) は 1-RTT handshake + AEAD-only cipher suite + 0-RTT (early data, replay risk あり) で TLS 1.2 から大きく整理されました。Perfect Forward Secrecy が default、RSA key exchange は廃止。 religious-corp の did:web は HTTPS 必須なので TLS 1.3 が事実上のベースラインです。

参考: RFC 8446, NIST SP 800-52 R2 TLS guidance

Domain 5 — Identity and Access Management

federation protocols

SAML 2.0 (OASIS 2005, XML-based, enterprise SSO), OAuth 2.0 (RFC 6749, authorization framework), OIDC (OpenID Connect, OAuth 上の authentication layer)。religious-corp の did:web + WebAuthn は OIDC と互換的に動くよう設計可能 (ADR-2605231525)。

WebAuthn / Passkey

WebAuthn (W3C 2019) は public-key cryptography ベースの passwordless authentication 標準。 Passkey は WebAuthn credential を device 間で同期可能にしたエコシステム実装。phishing-resistant が最大の利点。religious-corp Adherent identity は passkey + DID binding が default です。

参考: OASIS SAML 2.0, RFC 6749, OpenID Connect Core 1.0, W3C WebAuthn L3

Domain 6 — Security Assessment and Testing

テスト種別

vulnerability scanning (automated, signature-based), penetration testing (manual + creative, NIST SP 800-115), code review (static analysis + manual), red team (objective-based, multi-stage), blue team (defense practice), purple team (collaborative red + blue)。religious-corp 文脈では bug bounty 的な open-source 公開 review (Charter Rider §2(e) 適用) が中心スタンス。

脆弱性管理ライフサイクル

discovery → triage (CVSS scoring) → prioritization → remediation → verification → reporting。 CVSS v3.1 / v4.0 は Base + Temporal + Environmental の 3 metric group。

参考: NIST SP 800-115, FIRST CVSS v3.1 specification

Domain 7 — Security Operations

incident response

NIST SP 800-61 R2 は IR を 4 phase で扱います: preparation / detection & analysis / containment, eradication, recovery / post-incident activity。religious-corp の kazaori (ADR-2605263200) は civilian disaster response の religious-corp 実装で、 IR の隣接 domain として概念共有があります。

forensics 概念

chain of custody (証拠物の取扱記録の連続性) と order of volatility (RFC 3227: 揮発性の高い順から保全 — CPU register / cache → RAM → swap → disk → remote logs → archival media) が forensics の基本。

参考: NIST SP 800-61 R2, RFC 3227, ADR-2605263200 kazaori 災害対応

Domain 8 — Software Development Security

secure SDLC

NIST SSDF (Secure Software Development Framework, SP 800-218) は 4 practice group: Prepare the Organization / Protect the Software / Produce Well-Secured Software / Respond to Vulnerabilities。 religious-corp の Pregel cell ADR + Charter Rider §2 scan + e7m verify pre-commit hook が SSDF practice の religious-corp 実装に対応します。

OWASP Top 10

2021 版 (current): A01 Broken Access Control / A02 Cryptographic Failures / A03 Injection / A04 Insecure Design / A05 Security Misconfiguration / A06 Vulnerable & Outdated Components / A07 Identification & Authentication Failures / A08 Software and Data Integrity Failures / A09 Security Logging and Monitoring Failures / A10 Server-Side Request Forgery。

supply chain

SBOM (Software Bill of Materials, NTIA / SPDX / CycloneDX) は supply chain integrity の 要石。religious-corp の deps.toml は SBOM の機能を一部担います (modules + adrs registry)。

参考: NIST SP 800-218 SSDF, OWASP Top 10:2021, CycloneDX 1.6
